# ENGIverse 0.1.2 — تقرير التدقيق والإصلاح الهندسي

## النطاق

تم تنفيذ التدقيق على فرع `audit-fixes-0.1.2` فقط. لم يتم تعديل أو دفع أي تغيير إلى `main`، ولم يبدأ تطوير الإصدار 0.2. يظل المشروع scaffold تطويريًا وليس جاهزًا للإنتاج.

## المشكلات التي اكتُشفت وحلولها

### 1. غياب `frontend/package-lock.json` — عولج

كان `frontend/package.json` موجودًا دون lockfile، ما يمنع تثبيتًا قابلاً لإعادة الإنتاج ويجعل `npm ci` غير ممكن. تم إنشاء `frontend/package-lock.json` باستخدام npm من manifest الحالي، ثم التحقق من `npm ci` ونجاحه.

### 2. Dockerfile الأمامي كان يعتمد على wildcard وfallback غير قابل لإعادة الإنتاج — عولج

كان `frontend/Dockerfile` يستخدم `COPY package.json package-lock*.json ./` ثم يختار بين `npm ci` و`npm install`. بعد إضافة lockfile أصبح السلوك الأفضل هو النسخ الصريح للملفين واستخدام `npm ci --ignore-scripts`، لذلك تم تعديل Dockerfile إلى هذا النمط. لم يتم اختبار بناء الصورة لأن Docker غير مثبت في بيئة التنفيذ.

### 3. عدم توحيد رقم الإصدار — عولج

كان الإصدار `0.1.1` في `backend/pyproject.toml` وفي النص الظاهر داخل `frontend/src/App.tsx`، بينما كانت إعدادات أخرى على `0.1.2`. تم توحيدها إلى `0.1.2` في:

- Backend package metadata.
- Frontend `package.json` وlockfile.
- النص الظاهر في الواجهة.
- فحوصات البنية التي تمنع عودة عدم الاتساق.

### 4. اختبارات Backend تتأثر بمتغيرات بيئة خارجية — عولج

كان `backend/tests/conftest.py` يستخدم `os.environ.setdefault`. إذا كانت بيئة المطور أو CI تحتوي `APP_ENV` غير مدعوم، فإن الاختبارات تفشل قبل تحميل التطبيق. تم استبدال ذلك بتعيين صريح لقيم الاختبار قبل استيراد التطبيق، لضمان عزل الاختبارات وعدم تسرب إعدادات الإنتاج أو البيئة المحلية إليها.

### 5. متطلب PyYAML للفحص البنيوي غير معلن ضمن متطلبات التطوير — عولج

أضيف `PyYAML==6.0.2` إلى `backend/requirements-dev.txt`، لأن `scripts/static_checks.py` يعتمد عليه فعليًا.

### 6. قواعد Git كانت أضيق من المطلوب — عولج

تم توسيع `.gitignore` لاستبعاد بيئات `.venv*`، ومخرجات `build/` و`.vite/`، وقواعد البيانات المحلية (`*.sqlite`, `*.sqlite3`, `*.db`) والسجلات، مع إبقاء `package-lock.json` غير مستبعد.

### 7. ثغرات أدوات Frontend — عولج جزئيًا ومُوثّق

تم تحديث Vite إلى `5.4.21` وPostCSS إلى `8.5.32` مع تثبيت الإصدارات بدقة. أصبح تدقيق تبعيات الإنتاج (`npm audit --omit=dev`) بلا ثغرات. ما تزال هناك ثغرتان في تبعيات التطوير مرتبطة بـVite/esbuild، وإصلاح npm المقترح يتطلب ترقية كبرى إلى Vite 8 وتغييرات توافقية محتملة؛ لم تُفرض هذه الترقية ضمن نطاق 0.1.2.

## مراجعة قاعدة البيانات والأمان

- `DATABASE_URL` مطلوب ولا يملك قيمة افتراضية في إعدادات التطبيق.
- كلمات مرور الإنتاج النائبة أو القصيرة مرفوضة.
- كلمة المرور لا تظهر في تمثيل الإعدادات أو رابط قاعدة البيانات الآمن أو رسائل التحقق.
- قاعدة البيانات لا تنشر منفذًا في Compose الأساسي.
- شبكة قاعدة البيانات الداخلية مميزة عن شبكة الحافة.
- Backend يعمل بإعدادات `read_only` و`cap_drop: ALL` و`no-new-privileges` في Compose الأساسي.
- الاتصالات تستخدم `pool_pre_ping` وtimeouts وتدوير الاتصالات.
- فحص readiness يستخدم `SELECT 1` ولا يعرض تفاصيل خطأ الاتصال.
- CORS يرفض wildcard والمسارات غير الصحيحة.
- ملفات `.env` الحقيقية وملفات قواعد البيانات المحلية مستبعدة من Git.

## المشكلات التي لا تزال قائمة

1. لا توجد migrations فعلية بعد؛ مجلد Alembic لا يزال scaffold، وهذا متوافق مع نطاق 0.1.x لكنه يجب معالجته قبل نماذج الإصدار 0.2.
2. تبقى ثغرتان في أدوات التطوير عبر Vite/esbuild؛ تبعية الإنتاج بلا ثغرات حسب `npm audit --omit=dev`.
3. تحذير Starlette/AnyIO deprecated ظهر أثناء الاختبارات ولم يمنع النجاح، لكنه يحتاج متابعة عند ترقية الإطار.
4. لا توجد مصادقة أو تفويض بعد، وهو خارج نطاق 0.1.2 ومذكور ضمن انتقال 0.2.
5. لا يوجد اختبار ضغط حقيقي؛ لا يوجد أي دليل يسمح بادعاء دعم 100,000 مستخدم متزامن.

## خطة اختبار الأداء التدريجية

لا يدّعي هذا الإصدار دعم 100,000 مستخدم متزامن. يجب تنفيذ الاختبار على بيئة مماثلة للإنتاج وببيانات اصطناعية فقط:

1. **خط أساس:** 10 ثم 25 مستخدمًا متزامنًا، مدة 5 دقائق، مع قياس p50/p95/p99، معدل الأخطاء، throughput، CPU، الذاكرة، اتصالات PostgreSQL، وزمن الاستجابة.
2. **تدرج متوسط:** 50 ثم 100 ثم 250 ثم 500 مستخدم متزامن، مع ramp-up مضبوط واختبار soak لمدة 30–60 دقيقة.
3. **اختبار حدود:** زيادة الحمل حتى ظهور أول خرق للـSLO أو تشبع CPU/الذاكرة/اتصالات قاعدة البيانات، دون تخطي حدود البنية التحتية بأمان.
4. **اختبار الاستمرارية:** حمل ثابت 500–1000 مستخدم لمدة ساعتين على الأقل لرصد التسربات، تراكم الاتصالات، وتدهور latency.
5. **اختبار الفشل:** إيقاف/إعادة تشغيل PostgreSQL، فقدان backend replica، وامتلاء pool، ثم قياس التعافي وعدم تسرب الأسرار.
6. **اختبار التوسع:** زيادة replicas مع حساب `replicas × workers × (pool_size + max_overflow)` والتحقق من بقائه تحت `max_connections`، أو إدخال PgBouncer قبل أحمال أعلى.
7. **اختبار 100,000:** لا يُجرى إلا بعد نتائج المراحل السابقة، وبنية موزعة تشمل مولدات حمل متعددة، موازن حمل، عدة replicas، PostgreSQL مُدارًا عالي التوافر، PgBouncer، مراقبة مركزية، وحدود SLO واضحة.

الأدوات المقترحة: k6 أو Locust لمولد الحمل، Prometheus/Grafana للمقاييس، سجلات JSON مركزية، ومراقبة PostgreSQL للـconnections وlocks وslow queries. النتائج المطلوبة قبل أي ادعاء: معدل أخطاء، p50/p95/p99، RPS، CPU/Memory، DB connection utilization، saturation point، ونتائج التعافي.
